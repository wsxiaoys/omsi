### Response fields (verbatim)

`AsyncResponse` carries `id`, `polling_url`, `cost` ("Cost in credits for this request"),
`input_mp` ("Input megapixels (2 decimal places)") and `output_mp` ("Output megapixels (2 decimal
places)").

## What this establishes

- **Text-to-image and editing are the same endpoint**: the input images are optional, so a request
  without them is generation and a request with them is editing. BFL does not expose a separate
  klein edit path.
- **At most 4 input images**, matching the docs' "[klein] Up to 4" row. BFL's own schema annotation
  contrasts it with [pro]: "like Pro but max 4 images".
- **No sampling controls**: there is no `steps`, `guidance`, `num_inference_steps` or
  `guidance_scale` field, consistent with a 4-step distilled checkpoint. `seed`, size, format and
  safety tolerance are the only knobs.
- **Megapixel billing is first-party**: the response reports `input_mp` and `output_mp` separately,
  so input pixels are billed (see the pricing record).
- The schema label "(non-base)" is the first-party confirmation that the API serves the distilled
  checkpoint, not the Base weights.

## Gaps

- `width`/`height` have a documented minimum (64) but **no documented maximum**, so this page alone
  does not establish a 4MP ceiling for the 4B endpoint.
- No default output size is documented (`default: 0` on both dimensions is a sentinel, not a size).
- No stated step count, latency expectation, or resolution table.
- No `flux-2-klein-4b-preview` equivalent appears in the docs' preview list; whether this endpoint
  is a frozen snapshot is not stated here.

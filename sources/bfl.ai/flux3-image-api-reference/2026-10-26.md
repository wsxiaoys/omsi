# BFL official: FLUX 3 Image API reference (`POST /v1/flux-3-image`)

- Origin: Black Forest Labs, "Generate an image with FLUX 3",
  https://docs.bfl.ml/api-reference/utility/generate-an-image-with-flux-3.md
- Evidence kind: official documentation (API reference, request schema, limits)
- Publication date: not stated on page
- Capture date: 2026-10-26
- Relevant models: FLUX 3 Image (endpoint `POST https://api.bfl.ai/v1/flux-3-image`)

## Captured content

Request schema (`Flux3ImageInputs`), transcribed field by field:

| field | type | default | documented constraint |
| --- | --- | --- | --- |
| `prompt` | string | required | "Free-form prompt describing the image." |
| `images` | string or array | null | "each is an http(s) URL or base64, one to 10 total" |
| `aspect_ratio` | enum | `auto` | 15 fixed ratios plus `auto`; see below |
| `resolution` | enum | `1k` | `768sq`, `1k`, `1.5k`, `2k`, `4k`, `match_input` |
| `width` | int or null | null | `[256, 6256]`; set together with `height` |
| `height` | int or null | null | `[256, 6256]` |
| `safety_tolerance` | int | `2` | "from 0 to 7, with 0 the strictest" |
| `grounding` | bool | `true` | "web search and image search. When false, both are off" |
| `version` | string | `latest` | const `latest` |
| `user` | string or null | null | opaque end-user identifier, max 256 chars |

`additionalProperties: false`. There is **no** `seed`, `steps`, `guidance`, `mode`,
`output_format`, `negative_prompt`, or `input_image` field in the schema.

Verbatim descriptions of the fields that carry limits:

> `aspect_ratio` … Output aspect ratio. Under `auto` a ratio the prompt asks for wins, otherwise
> the output keeps the first reference image's framing; without references the prompt decides,
> else 1:1.

> `resolution` … Image resolution class, an equal-pixel-area tier: `768sq`, `1k` (default),
> `1.5k`, `2k`, or `4k`. Exact dimensions vary with the aspect ratio. `match_input` (edits only):
> the output keeps the first reference's own size (shrunk to 4 MP when larger), or its nearest
> tier when aspect_ratio is set. Ignored when width and height are set.

> `width` … Exact output width in pixels, [256, 6256]; set together with height. Overrides
> resolution and aspect_ratio.

> `height` … Exact output height in pixels, [256, 6256]; width x height at most 16822272 pixels,
> and at most 4194304 with reference images.

> `safety_tolerance` … Harm moderation tolerance from 0 to 7, with 0 the strictest. The route and
> organization determine the approved maximum and per-category ceilings. Unapproved levels return
> 422 with approved levels.

> `version` … Endpoint version. `latest` (default) serves the current release; dated pinnable
> release tags are added here as they are published.

Aspect-ratio enum, in schema order: `21:9`, `2:1`, `16:9`, `3:2`, `7:5`, `4:3`, `5:4`, `1:1`,
`4:5`, `3:4`, `5:7`, `2:3`, `9:16`, `1:2`, `9:21`, plus `auto`.

Response (`AsyncResponse`): `id`, `polling_url`, and nullable `cost` ("Cost in credits for this
request"), `input_mp`, `output_mp` (megapixels, 2 decimals).

The reference page's own examples show layout prompts: a JSON array appended to `prompt` with
`{"id", "bbox", "desc"}` for placement and `{"id", "from", "src_bbox", "tgt_bbox", "desc"}` for
box-targeted edits, with ids such as `animal_1` and reference tokens `ref_image_0`.

## What this establishes

- **16.8 MP output ceiling** (16,822,272 px) and a **4 MP ceiling once reference images are
  present**; refs are 1–10 images, each at most 16 MP and at least 256×256 (the 256 minimum and the
  16 MP rejection are stated on the text-to-image page, see
  `../flux3-image-text-to-image/2026-10-26.md`).
- No reproducibility control: `seed` is absent and unknown fields are rejected
  (`additionalProperties: false`), so a given request cannot be replayed exactly.
- No sampling controls. Like FLUX.2 [pro], inference configuration is not exposed.
- `safety_tolerance` runs to 7 here, unlike the 0–4 range both captured hosts expose.
- No dated snapshot exists yet: `version` is pinned to the string `latest`, with dated tags
  promised "as they are published".

## Gaps

- The schema does not say what output format/compression the first-party endpoint returns.
- No documented latency, throughput, or queue behaviour beyond the polling contract.
- `match_input` is documented only for edits; its behaviour when width/height are also set is
  described but not illustrated.

# BRIA AI docs: rate limits and error contract

- Origin: Bria developer docs, "Rate limits and errors",
  https://docs.bria.ai/getting-started/rate-limits-and-errors
- Evidence kind: official documentation (vendor platform limits)
- Publication date: none stated; read 2026-10-26
- Capture date: 2026-10-26
- Relevant models: platform-wide; applies to FIBO Edit / FIBO-Edit 1.5 requests made first-party

## Captured content (verbatim excerpts)

> Limits apply per organization and per endpoint, measured in requests per minute.
>
> | Plan | Requests per minute per endpoint |
> | --- | --- |
> | Free | 10 |
> | Pay-as-you-go | 60 |
> | Enterprise | 1000, customizable per organization |

> Above the limit the API returns `429 Too Many Requests`. Status endpoint calls count toward the limit,
> so poll at a sensible interval or use webhooks.

> **Handling 429** — Retry with exponential backoff and jitter, honor `Retry-After` when present, and cap
> concurrency on your side so a burst does not turn into a wave of retries.

Error body shape, verbatim example:

```json
{
  "request_id": "9d4a1a2f5c7e4b6f8a0c2d3e4f5a6b7c",
  "error": { "code": 422, "message": "Unprocessable Entity", "details": "Prompt failed content moderation." }
}
```

> Asynchronous jobs report failures through the status endpoint: `status` is `ERROR` and the same
> `error` object is included.

## Notes

- Status polling counts against the same per-endpoint limit, which matters for the async-by-default v2
  contract that FIBO Edit 1.5 used.
- The SDKs retry `429`, `502`, `503`, `504` on status polling (3 attempts) but never retry `run` or
  `submit`, "so a job is never started twice".

## Gaps

- No stated limit on concurrent jobs, image size, or payload size.
- Limits are per endpoint rather than per model (inference from the table header "per organization and
  per endpoint"); no per-model quota is published.

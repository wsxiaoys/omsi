## Service description (verbatim)

> Step 2 detects subjects in images and supports returning mask images corresponding to the subjects.
> This step can be skipped if there's no need to specify a subject to speak during video generation.

## Parameters

| Name | Type | Required | Value |
| --- | --- | --- | --- |
| `req_key` | string | Yes | "Service identifier: realman_avatar_object_detection_cv" (marked "fixed") |
| `image_url` | string | Yes | "URL link of the portrait image" |
| `callback_url` | string | No | terminal-state POST callback |

Image requirements repeat the generator's: JPG/PNG/JFIF, <5 MB, <4096×4096.

## Response (verbatim)

> status: Whether the subject is detected. 0 means no subject is detected, and 1 means the subject is
> detected.

> object_detection_result.mask.url (Field to focus on): The order of the URL list and the subjects in
> the input images are sorted in descending order of mask area (from largest to smallest). If you need
> to preview the mask images, you can download them via the URLs, manually change the file name
> extension to .png, and save them as .png files before viewing.

Example body: `{"code":0,"object_detection_result":{"mask":{"url":["https://xxxxx"]}},"status":1}`

## Summary

Returns one mask URL per detected subject, ordered largest-first, which the caller passes as
`mask_url` to `realman_avatar_picture_omni15_cv` to decide which subject speaks. The ordering is the
only selection key the vendor documents; there is no bounding box, label, or subject description in
the response, so "who is mask index 1" has to be discovered by rendering the PNG.

## Gaps

- No price, rate limit, or latency for this helper call.
- No cap on the number of subjects returned, and no accuracy claim.
- No indication that the host routes (fal, Replicate) run detection; fal exposes a raw `mask_url`
  input instead, leaving mask creation entirely to the caller.

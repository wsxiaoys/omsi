## Captured content

> Cartesia exposes three ways to turn text into speech. The same models, voices, and core parameters
> apply everywhere.

| | Multiple generations per connection | Timestamps | Continuations |
| - | - | - | - |
| WebSocket | Yes | Yes | Yes |
| Bytes | No (one `POST` per generation) | No | No |
| SSE | No (one `POST` per generation) | Yes | No |

> If you care about time-to-first-byte on every turn, remember that a new HTTPS request pays for TCP
> and TLS again; that overhead is often on the same order as TTFB for the audio itself. WebSocket
> amortizes that cost when you keep the socket open.

> SSE remains available largely for backward compatibility and for teams that standardize on
> Server-Sent Events.

Continuations: a partial utterance is sent as several WebSocket messages sharing a `context_id`, with
`continue: true` on partials and `continue: false` on the last part; "multiple `context_id` values on
one connection" allow overlapping utterances.

## Summary

All three endpoints stream audio and share the model IDs. The practical differences are timestamps
(SSE and WebSocket), continuations/multiplexing (WebSocket only), and container support (WAV/MP3 only
on bytes). Cartesia itself states that connection setup can be "on the same order" as audio TTFB for
HTTP routes — relevant to any latency comparison, because a sub-90 ms model number excludes that cost.

## Gaps

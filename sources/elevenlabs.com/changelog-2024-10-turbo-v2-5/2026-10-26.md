# ElevenLabs docs changelog: two 2024 entries that name `turbo_v2.5`

- Origin: ElevenLabs docs changelog entries
  <https://elevenlabs.io/docs/changelog/2024/10/13> and
  <https://elevenlabs.io/docs/changelog/2024/10/20> (read as Markdown via `Accept: text/markdown`)
- Evidence kind: official documentation (dated release notes)
- Publication date: 2024-10-13 and 2024-10-20 (dates are the entry titles)
- Capture date: 2026-10-26
- Relevant models: `eleven_turbo_v2_5`, `eleven_turbo_v2`

## 2024-10-13 entry (verbatim)

> ## Model
>
> - **Stability Improvements**: Significant audio stability improvements across all models, most
>   noticeable on `turbo_v2` and `turbo_v2.5`, when using:
>   - Websockets
>   - Projects
>   - Reader app
>   - TTS with request stitching
>   - ConvAI
> - **Latency Improvements**: Reduced time to first byte latency by approximately 20-30ms for all
>   models.

## 2024-10-20 entry (verbatim)

> ## API
>
> - **Normalize Text with the API**: Added the option normalize the input text in the TTS API. The new
>   parameter is called `apply_text_normalization` and works on all models. For v2.5 models, this
>   feature is available with Enterprise plans only.

## What this establishes

- `turbo_v2.5` (the changelog's dotted spelling of `eleven_turbo_v2_5`) was in production by
  2024-10-13, three months after the 2024-07-19 launch post — independent confirmation that the
  launch date is 2024 and that this model predates the roster window by years.
- **Text normalization was plan-gated for v2.5 models**: `apply_text_normalization` "works on all
  models", but "for v2.5 models, this feature is available with Enterprise plans only". Both host
  schemas (fal, Replicate) expose the parameter without restating the plan restriction, so a host
  caller may be passing a parameter that is only honoured upstream on Enterprise plans.
- The changelog records no deprecation entry for `eleven_turbo_v2_5`; the model's move to the
  "Older Models" / deprecated table happened without a changelog note that this capture could find.

## Gaps

- The changelog does not give absolute latency figures, only deltas ("approximately 20-30ms" time to
  first byte).
- Whether the Enterprise-only restriction on `apply_text_normalization` still applies at capture is
  not stated on the current API reference, which describes the parameter with no plan caveat. The
  contradiction is unresolved.

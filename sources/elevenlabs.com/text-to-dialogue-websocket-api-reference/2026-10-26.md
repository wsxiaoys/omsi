# ElevenLabs API reference: Text to Dialogue WebSocket (`/v1/text-to-dialogue/stream-input`)

- Origin: ElevenLabs, API reference "WebSocket — GET /v1/text-to-dialogue/stream-input",
  <https://elevenlabs.io/docs/api-reference/text-to-dialogue/ttd-websocket> (reference body and
  embedded AsyncAPI 2.6.0 specification, read from the rendered document)
- Evidence kind: official documentation (API reference and protocol schema)
- Publication date: not stated on page
- Capture date: 2026-10-26
- Relevant models: `eleven_v4_turbo`, `eleven_v4`, `eleven_v3`, `eleven_v3_conversational`

## Captured content (verbatim)

### Scope and default model

> The connection uses Eleven v3 and v4 dialogue models (`model_id` must start with `eleven_v3` or
> `eleven_v4`). The default model is `eleven_v3_conversational`.

### Session setup and voice registration

> After connecting, the first JSON message **must** include `voices` (voice IDs to register for the
> session) and credentials if not already sent via headers or query string.

> Optional `voice_settings` and `pronunciation_dictionary_locators` are only accepted on the first
> message.

> For `eleven_v3_conversational` and `eleven_v4` models, only **one** voice ID may be registered. For
> `eleven_v3`, you may register up to **10** voices.

### Streaming text and buffering

> Send `inputs`: an array of `{ "text", "voice_id", "new_turn"? }`. Text for the same turn is
> buffered until the server has enough context (at least ~40 characters and 8 words), then partial
> audio chunks are emitted.

> Set `new_turn` to `true` (or switch `voice_id`) to finalize the current prosody segment and start a
> new speaker turn.

### Control messages

> `flush`: force generation of any buffered text without closing the socket.

> `close_socket`: flush remaining audio, send a final message, and close the connection.

> `keep_alive`: reset the **20 second** receive timeout (no generation).

### Query parameters (AsyncAPI `bindings.ws.query`)

| Parameter | Type | Default / constraint |
| --- | --- | --- |
| `model_id` | string | default `eleven_v3_conversational` |
| `output_format` | "Any type" — no enum in the schema | not stated |
| `language_code` | string | — |
| `sync_alignment` | boolean | default `false` |
| `apply_text_normalization` | "Any type" | — |
| `seed` | integer | min 1, max 4294967295 |
| `enable_logging` | boolean | default `true` |

### `voice_settings` on the socket (verbatim schema descriptions)

> `stability` … minimum 0, maximum 1, default 0.5 … "Lower values introduce broader emotional range
> for the voice. Higher values can result in a monotonous voice with limited emotion."

> `clone_strength` … minimum 0, maximum 1 … "Controls how closely the voice matches the professional
> voice clone samples, from 0 (low) to 1 (high). We recommend 0 for most use cases. Increase this
> value only if you experience issues with the default settings. Only applies to professional voice
> clones fine-tuned for the selected v4 model."

> "Voice settings for dialogue generation. Only `stability` is supported for `eleven_v3` dialogue
> models."

### Server message types

Audio chunks carry `audio` ("Base64-encoded audio bytes for the selected `output_format`") plus
optional `alignment` / `normalized_alignment`; the socket also emits
`is_final_audio_for_turn`, `is_final` (end of the closing flush sequence) and typed errors with
`message`, `error` (for example `authentication_required`) and `code`.

### Residency hosts

`wss://api.elevenlabs.io/` (default), `api.us.elevenlabs.io`, `api.eu.residency.elevenlabs.io`,
`api.in.residency.elevenlabs.io`, `api.sg.residency.elevenlabs.io`.

## Summary

This is the protocol-level reference for the route ElevenLabs names as the launch path for
`eleven_v4_turbo`. It fixes several things the capability pages leave open:

- The socket's **default model is `eleven_v3_conversational`**, not a v4 model — a Turbo caller must
  pass `model_id` explicitly, and a missing parameter silently selects the older model.
- Only `stability` and the PVC-only `clone_strength` are accepted as `voice_settings` on this socket;
  **`similarity_boost` is absent**, although the HTTP Text to Speech reference documents it for v4.
- `output_format` is untyped in the schema ("Any type"), so the reference itself does not enumerate
  which sample rates or codecs the Turbo socket can emit.
- `seed` and `enable_logging` are available, so best-effort determinism and the Enterprise
  zero-retention flag reach the socket route.
- Voice registration contradicts the companion comparison guide: this reference says `eleven_v4` is
  limited to one registered voice and `eleven_v3` to ten, and does not mention `eleven_v4_turbo` at
  all; the guide says `eleven_v4` allows ten and `eleven_v4_turbo` only one
  (`../tts-vs-ttd-websockets/2026-10-26.md`).

## Gaps

- No maximum text length per message, per session or per connection is stated anywhere in the
  reference; the 2,000-character reliability guidance lives on the Text to Dialogue capability page,
  not here.
- No latency, throughput or concurrency figure; no session-pool size per plan.
- No output-format enumeration and no default stated for the socket, so the sample rate ceiling for
  Turbo over WebSocket cannot be read from this page.
- No watermarking statement.
- No date, so it cannot be ordered against the 2026-09-28 launch.

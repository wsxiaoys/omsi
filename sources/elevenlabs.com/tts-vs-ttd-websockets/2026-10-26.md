## Captured content (verbatim)

### Which socket for which model

> Use the **Text to Speech (TTS) WebSocket** when you stream plain text for **one voice per
> connection** (the voice is fixed in the URL) and you want **non-v3** models such as Flash or
> Multilingual v2, optional SSML, chunk schedules, or the **multi-context** variant for agent-style
> interruption handling.

> Use the **Text to Dialogue (TTD) WebSocket** when you need **Eleven v3** dialogue behavior:
> expressive delivery, **per-chunk `voice_id`**, turn boundaries (`new_turn`), and the same
> dialogue-oriented buffering used for v3 on the server.

### Comparison table rows that constrain Eleven v4 Turbo

| Row | Text to Speech WebSocket | Text to Dialogue WebSocket |
| --- | --- | --- |
| URL | `wss://api.elevenlabs.io/v1/text-to-speech/{voice_id}/stream-input` | `wss://api.elevenlabs.io/v1/text-to-dialogue/stream-input` |
| Models | "Flash, Multilingual v2, and other supported TTS models. **No** `eleven_v3` or `eleven_v4` on this endpoint." | "**`model_id` must start with `eleven_v3` or `eleven_v4`** (for example `eleven_v4` or `eleven_v4_turbo`)" |
| Buffering / scheduling | "Chunk length schedule and related TTS WebSocket controls" | "Server buffers until enough text is present (roughly **40 characters and 8 words**) before emitting audio, unless you **`flush`**" |
| Multi-speaker on one socket | multi-context socket, "not multi-speaker dialogue semantics" | "Up to **10** registered voices for `eleven_v4`; **`eleven_v4_turbo` allows only one** registered voice" |
| Inactivity | "Configurable `inactivity_timeout` (TTS WebSocket query)" | "**Fixed 20s** between client messages unless you send **`keep_alive`**" |
| Concurrency | "Only active generation time counts toward your plan's concurrency limit; an idle open socket does not count" | "Each open connection holds one dialogue session from a separate pool for its whole lifetime; generation over the connection does not consume standard concurrency" |
| Alignment | "Optional `sync_alignment` (TTS field naming in API reference)" | "Optional `sync_alignment`; JSON uses **snake_case** fields on responses (for example `is_final`, `char_start_times_ms`)" |

The TTD column's "when it is the better fit" list names "**Eleven v4** dialogue (expressive tags,
conversational pacing, multi-speaker lines)" and "**v4-only** dialogue generation on the server".

## Summary

This is the vendor's own side-by-side of its two streaming protocols, and it is the only captured page
that states the **Turbo-specific** WebSocket constraints:

- `eleven_v4_turbo` is reachable on the Text to Dialogue WebSocket and **not** on the Text to Speech
  WebSocket ("No `eleven_v3` or `eleven_v4` on this endpoint").
- Turbo allows **one** registered voice per connection, where plain `eleven_v4` is listed at up to 10.
- The socket has a **fixed 20 s** receive timeout that only `keep_alive` resets, and generation is
  buffered server-side until roughly 40 characters and 8 words are available unless the client
  `flush`es. Both are latency-shaping constraints that sit on top of the ~100 ms inference claim.
- Streaming a dialogue costs a **dialogue session** from a separate pool, not standard TTS
  concurrency — the consumption model differs from a request/response TTS call.

## Gaps

- No date on the page; it cannot be ordered against the 2026-09-28 launch or the 2026-10-19 agent
  default change.
- The page gives no latency numbers and no output-format list for the TTD socket.
- It does not say whether `eleven_v4_turbo` is also callable on the HTTP Text to Speech endpoint or
  only on the dialogue routes.
- The "one registered voice" rule for Turbo conflicts with the TTD WebSocket API reference's own
  voice-registration rule, which names `eleven_v4` (not Turbo) as the one-voice model — see
  `../text-to-dialogue-websocket-api-reference/2026-10-26.md`.
- No watermarking statement for streamed audio.

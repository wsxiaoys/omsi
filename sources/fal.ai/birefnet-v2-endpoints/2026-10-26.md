## What "v2" is, on the evidence

The queue OpenAPI `x-fal-metadata.about` strings are fal's internal handler names:

| Endpoint | `about` |
| --- | --- |
| `fal-ai/birefnet` | `Remove Background Http` |
| `fal-ai/birefnet/v2` | `Remove Background Http V2` |
| `fal-ai/birefnet/v2/video` | `Remove Background Http Video V2` |

So "V2" labels fal's *HTTP handler* generation for the same upstream model family, not a new
BiRefNet checkpoint (the upstream repository has no v2 release; see
[releases record](../../github.com/birefnet-releases/2026-10-26.md)). The evidence for that reading:

1. fal's own handler names say "Remove Background Http V2".
2. The upstream repo's only tag is `v1`, and its README never uses "v2" except as the fal URL.
3. Both fal endpoints serve the same published checkpoints; the v2 endpoint simply exposes more of
   them (below).

## v1 vs v2 endpoint surface (from the two schemas)

| Input | `fal-ai/birefnet` (v1) | `fal-ai/birefnet/v2` |
| --- | --- | --- |
| `image_url` | required | required |
| `model` enum | `General Use (Light)`, `General Use (Heavy)`, `Portrait` | `General Use (Light)`, `General Use (Light 2K)`, `General Use (Heavy)`, `Matting`, `Portrait`, `General Use (Dynamic)` |
| `model` default | `General Use (Light)` | `General Use (Light)` |
| `operating_resolution` enum | `1024x1024`, `2048x2048` | `1024x1024`, `2048x2048`, `2304x2304` (2304 "only available for the 'General Use (Dynamic)' model") |
| `operating_resolution` default | `1024x1024` | `1024x1024` |
| `output_format` | `webp`, `png`, `gif` (default `png`) | same |
| `output_mask` | yes (default false) | yes (default false) |
| `refine_foreground` | yes (default true) | yes (default true) |
| `mask_only` | absent | present, default false: "When set to `True`, only the mask will be returned and foreground refinement will be skipped." |
| `sync_mode` | yes | yes |

**The checkpoint mapping changed between the two endpoints.** v1's description (verbatim):

> - 'General Use (Light)': BiRefNet-DIS_ep580.pth
> - 'General Use (Heavy)': BiRefNet-massive-epoch_240.pth
> - 'Portrait': BiRefNet-portrait-TR_P3M_10k-epoch_120.pth

v2's description (verbatim):

> - 'General Use (Light)': BiRefNet
> - 'General Use (Light 2K)': BiRefNet_lite-2K
> - 'General Use (Heavy)': BiRefNet_lite
> - 'Matting': BiRefNet-matting
> - 'Portrait': BiRefNet-portrait
> - 'General Use (Dynamic)': BiRefNet_dynamic

with the prose (verbatim): "The 'General Use (Light)' model is the original model used in the
BiRefNet repository. The 'General Use (Light 2K)' model is the original model used in the BiRefNet
repository but trained with 2K images. The 'General Use (Heavy)' model is a slower but more accurate
model. The 'Matting' model is a model trained specifically for matting images. The 'Portrait' model
is a model trained specifically for portrait images. The 'General Use (Dynamic)' model supports
dynamic resolutions from 256x256 to 2304x2304. The 'General Use (Light)' model is recommended for
most use cases."

**Documented contradiction.** fal's v2 labels are inverted against the upstream sizes. The
"General Use (Heavy)" slot is mapped to `BiRefNet_lite`, which is the ~44.4 M-parameter Swin-T
checkpoint, while "General Use (Light)" is mapped to `BiRefNet`, the ~220.7 M-parameter Swin-L
checkpoint (parameter counts from the HF records; sizes from the paper's Table 7). fal also calls
"Heavy" "slower but more accurate", while the upstream model zoo reports the Swin-T general
checkpoint as *less* accurate than Swin-L on DIS-VD (0.882/0.830/1175 vs 0.911/0.875/1069). In v1
both "Light" and "Heavy" were Swin-L checkpoints (`BiRefNet-DIS_ep580` vs
`BiRefNet-massive-epoch_240`), so the labels were at least consistent with equal model size there.
Which checkpoint `Heavy` actually loads at inference is **not resolved by this evidence**; a caller
should map by the checkpoint name, not by the Light/Heavy adjective.

Also note the v2 `Light` default is now the *general-use* `BiRefNet` weights, whereas v1's `Light`
default was the DIS5K-only `BiRefNet-DIS_ep580` checkpoint — a default change, not a model release.

## Video endpoint (`fal-ai/birefnet/v2/video`)

Published 2025-10-26T18:13:23.036Z — the only fal BiRefNet endpoint inside the roster window.
Inputs: `video_url` (required), `model` (same six values as the image v2 endpoint), `operating_
resolution` (`1024x1024`/`2048x2048`/`2304x2304`), `output_mask`, `video_quality`
(`low`/`medium`/`high`/`maximum`, default `high`), `video_output_type`
(`X264 (.mp4)`/`VP9 (.webm)`/`PRORES4444 (.mov)`/`GIF (.gif)`, default `X264 (.mp4)`),
`video_write_mode` (`fast`/`balanced`/`small`, default `balanced`). Outputs: `video` and optional
`mask_video`. The schema's example output is 1920×1080, 24 fps, 8 s, 192 frames.

The video endpoint carries the same model enum and the same `Heavy` → `BiRefNet_lite` mapping as the
image endpoint. fal documents no per-frame temporal smoothing, and no frame-rate cap.

## Pricing

fal's model page for `fal-ai/birefnet/v2` renders, verbatim, at capture:

> Your request will cost $ 0 per compute second .

and the page's embedded billing payload is:

```
"endpointBilling":{"endpoint":"fal-ai/birefnet/v2","billing_unit":"compute seconds","price":0,
"provider_type":"fal","is_partner_api":false,...}
```

with `publicEndpointBilling` identical. So fal bills this endpoint in **compute seconds** and, at
capture, publishes **$0** for it. `$0` is the literal published value; it may mean a free/legacy
endpoint, an unpopulated price field, or a promotional rate — the page does not say, and there is no
authenticated pricing API available to this capture (`https://api.fal.ai/v1/models/pricing` returns
`authorization_error`). fal's public pricing page lists per-GPU hourly rates (B300, GB200, B200,
H200, H100, RTX PRO 6000) but no A100 row and no BiRefNet row, so a per-image cost cannot be
reconstructed from fal's published material.

`machineType: "GPU-A100"` in the catalogue is the only hardware statement for the image endpoints.

## Gaps

- **No per-image price** is derivable: billing is compute-second, the published unit price is `$0`,
  and fal publishes neither the per-request compute time nor an A100 hourly rate on the pricing page.
- **No quality, latency, or throughput measurements** are published on the endpoint page. The
  catalogue's `high-res` and `segmentation` tags and the "bilateral reference framework" description
  are restatements of the paper, not measurements.
- **`releaseDate` is `undefined`** in the page payload; only catalogue `date`/`publishedAt` are
  available, and those are day-granular for the two image endpoints.
- fal's catalogue dates may be backfilled: the v1 endpoint's `date` is 2024-02-27, while the upstream
  README dates fal's first BiRefNet deployment to 2024-04-09.
- No documented safety filter, moderation policy, or content restriction appears in the schemas.
- No documentation of which upstream commit or weight file hash each endpoint loads, or when it was
  last rebuilt (only `updated_at` 2026-07-10 for the metadata record).

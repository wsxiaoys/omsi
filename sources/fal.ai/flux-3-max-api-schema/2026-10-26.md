# fal.ai: OpenAPI schema for the `blackforestlabs/flux-3-max/*` endpoints

- Origin: fal.ai queue API schemas,
  `GET https://fal.ai/api/openapi/queue/openapi.json?endpoint_id=blackforestlabs/flux-3-max/text-to-video`
  and the same request for `.../image-to-video` and `.../keyframes-to-video`
- Evidence kind: provider documentation (machine-readable request/response schema)
- Publication date: n/a — live schema
- Capture date: 2026-10-26
- Relevant models: FLUX 3 Max (all three endpoints)

## Captured parameters (verbatim descriptions, enums and defaults)

All three input schemas share the same generation controls. Response bodies are 7,222 /
7,843 / 8,429 bytes, so all three endpoints are callable and documented.

| Field | Type | Default | Enum / notes |
| --- | --- | --- | --- |
| `prompt` | string | required (`minLength: 1`) | "The text prompt describing the video you want to generate." |
| `duration` | integer | 5 | enum 5–20 inclusive: "Duration of the generated video in seconds." |
| `resolution` | string | `720p` | enum `720p`, `1080p` — "Resolution of the generated video." |
| `reasoning_level` | string | `high` | enum `low`, `high` — "How much effort the harness spends reasoning about the given prompt. Higher reasoning effort means slower generation time." |
| `aspect_ratio` | string | `auto` | enum `auto`, `21:9`, `2:1`, `16:9`, `4:3`, `1:1`, `3:4`, `9:16` — "`auto` uses 16:9 for text prompts and follows the first image otherwise." |
| `generate_audio` | boolean | `true` | "Whether to generate audio for the video." |
| `seed` | integer or null | — | "The seed to use for the generation. Random when not provided." |

Endpoint-specific inputs:

- image-to-video: `image_url` ("PNG, JPEG or WebP, the first frame") and optional `end_image_url`
  ("the last frame").
- keyframes-to-video: `keyframes`, an array.

Output schema (`VideoFile` plus `seed` and `timings`): `timings` is documented as "`inference`:
seconds the model spent denoising the video. Excludes prompt expansion, decoding and upload." The
`video` example object is `{ "fps": 24, "width": 1280, "height": 704, "num_frames": 121,
"duration": 5.041666666666667 }`.

## Findings that matter for limits

- **Duration is 5–20 s in whole seconds**, matching the base FLUX 3 Video limit. There is no
  separate Max-specific length cap.
- **`resolution` accepts `720p` and `1080p`.** This contradicts the landing page's 720p-only price
  block and the catalogue descriptions' "Output: 720p video". The schema is the more precise
  document, but nothing captured states what the 1080p path actually does (upscale vs native), so
  the contradiction is left open.
- **`reasoning_level` is exposed**, which the first-party FLUX 3 Video API does not offer. BFL's
  `POST /v1/flux-3-video` inputs are `prompt`, `mode`, `aspect_ratio` (including `9:21`, which fal
  does not offer), `duration`, `resolution` (`hd`/`fhd`/`qhd`/`uhd`), `version`, `generate_audio`,
  `safety_tolerance`, `draft` — so fal swaps BFL's draft/upscale resolution classes and
  `safety_tolerance` for `reasoning_level`, `seed` and a `720p`/`1080p` resolution enum. Whether
  `high` is a prompt-expansion pass or extra sampling is not stated beyond "How much effort the
  harness spends reasoning about the given prompt".

## Oddity

The schema component titles are `AlligatorTextToVideoInput` / `AlligatorImageToVideoInput` /
`AlligatorKeyframesToVideoInput`. "Alligator" appears to be an internal codename left in the
published schema. It is recorded here only as an artifact; nothing in the evidence maps it to a
product name.

## Gaps

- No cost field, no per-request maximum on prompt length, no rate limits, no safety/moderation
  parameters in the schema.
- No statement of what happens when `resolution: 1080p` is combined with the 720p-based promo
  pricing.

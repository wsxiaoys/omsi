`hostingType: "serverless"` means fal reports running the model on its own infrastructure, not
proxying Krea's API. For contrast, the same catalogue lists Krea 2 Medium and Krea 2 Large as
`hostingType: "proxy"`. So fal is an independent host deployment of Krea 3, and its behavior may
diverge from Krea's own API.

The model page carries the badges "Inference" and "Commercial use"; `licenseType: "commercial"` is
fal's catalogue field about use through fal, not a Krea licence statement.

## Pricing (verbatim `pricingInfoOverride`)

> Billed per megapixel at **$0.025**/MP, counting the output image plus each reference image as the
> model processes it (references larger than the output are counted at the output's size). 1 MP =
> 1024×1024 pixels.

This is a per-megapixel schedule, unlike Krea's first-party per-tier schedule. The actual cost
therefore depends on the pixel dimensions of the output and references, which the schema does not
fix for the named `1K`/`2K` presets. `auto` is documented as "about 2048×2048" (≈4.19 MP).

## Edit schema (`krea/v3/edit`)

Selected input fields, verbatim descriptions:

| Field | Type / default | Description |
| --- | --- | --- |
| `prompt` | string, 1–5000 chars, required | "Description of the image to generate." |
| `image_urls` | array, 1–8, required | "Reference images to edit or combine (1-8). Order sets the `<image-N>` tags." |
| `model` | enum `berry` (default), `jam` | "Model variant: berry favors quality, jam favors speed." |
| `image_size` | preset or `{width,height}`, default `auto` | "Output size, rounded up to multiples of 16, at most 4,220,160 total pixels (1680×2512). `auto` lets the prompt expander pick the aspect ratio at about 2048×2048." |
| `reasoning_level` | enum `low`, `medium` (default), `high`, `ultra` | See below. |
| `negative_prompt` | string, max 1024, default "" | "What to keep out of the image. Used by berry only." |
| `seed` | integer or null | "Latent noise seed. Use a new seed when editing a previous output again." |
| `output_format` | `png` (default) or `jpeg` | Output image format. |
| `enable_safety_checker` | boolean, default true | "Check output images for unsafe content. Disabling requires account authorization." |
| `sync_mode` | boolean, default false | Return data URIs instead of saving in request history. |

`reasoning_level` description (verbatim):

> How much effort the harness spends reasoning about the given editing task. Higher reasoning effort
> means slower generation time. high plans the edit with segmentation, web search and reference
> photos, keeps unedited areas of a single input image, corrects required text, and bills a flat
> $0.125 (5 megapixels) more per request. low and medium bill $0.025 per megapixel of the output plus
> each reference (references larger than the output count as the output size). ultra generates at 2K
> with Krea's ultra thinking mode, ignores image_size and negative_prompt, and bills a flat price by
> reference count: $0.27 for 1, $0.30 for 2, $0.32 for 3, $0.35 for 4, plus $0.0275 per reference
> past 4.

Output schema includes `images[]`, `seed`, `prompt` ("Prompt used for generation, after expansion"),
`timings` ("Seconds spent in each generation stage; `inference` is the total GPU sampling time"), and
`has_nsfw_concepts[]`.

## Text-to-image schema (`krea/v3/text-to-image`)

Same `model` (berry/jam), `image_size`, `negative_prompt`, `seed`, safety checker, and output shape,
but `reasoning_level` is only:

| Enum | Description |
| --- | --- |
| `low` | (no separate description) |
| `medium` (default) | "How much effort the harness spends reasoning about the given prompt. Higher reasoning effort means slower generation time. Both levels bill $0.025 per output megapixel." |

So fal's text-to-image endpoint does **not** expose `high` or `ultra`, while its edit endpoint does.
`image_urls` is absent and `prompt` is the only required field.

## Realtime schema (`krea/v3/realtime`)

Inputs are `prompt` ("Edit instruction. Refer to the input frame as `<image-1>`."), `seed`, and an
optional `image_url`. The image field says frames "are resized to 768x768" and the image "stays for
the session: later messages without it edit the same image, and an empty string clears it to
generate from the prompt alone." Output is an edited frame as a JPEG data URI.

This is a session-oriented endpoint, not the request/response edit API. Krea's launch post says
"Krea 3 isn't real time yet"; fal sells a "Krea 3 Realtime" endpoint. The relationship between the
two is not documented.

## Gaps

- No prose readme on the fal page (the page is a client-rendered playground), so capability claims
  come from the catalogue description and schema text, not from a fal-authored model card.
- The related-family rows are catalogue metadata only; no Krea 2 or FLUX.1 Krea capability claims are
  made here.
- The mapping between fal's four `reasoning_level` values and Krea's three `thinking_mode` values is
  not documented. fal's `medium` is the default while Krea's `fast` is the default; whether fal's
  `low` and `medium` both map to Krea `fast` is unknown.
- fal's `high` description adds capabilities not mentioned in Krea's docs (segmentation, web search,
  reference photos, text correction). Whether these are fal-side additions or an unlisted part of
  Krea's `high` mode is not stated.
- The exact pixel dimensions of the `1K`/`2K` presets are not in the schema; only `auto`'s
  "about 2048×2048" and the 4,220,160-pixel cap are.
- No revision or snapshot field, so which Krea 3 build fal serves is unknown.
- No independent latency or quality measurement; the schema exposes `timings` per request but no
  aggregate.

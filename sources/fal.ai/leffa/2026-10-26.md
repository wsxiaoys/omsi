- Origin: fal.ai public model catalogue, metadata API, OpenAPI queue schemas, and model pages:
  - `GET https://fal.ai/api/models?keywords=leffa` (gallery JSON)
  - `GET https://api.fal.ai/v1/models?endpoint_id=fal-ai/leffa/virtual-tryon` and `…/pose-transfer`
  - `GET https://fal.ai/api/openapi/queue/openapi.json?endpoint_id=fal-ai/leffa/virtual-tryon` and `…/pose-transfer`
  - model pages `https://fal.ai/models/fal-ai/leffa`, `…/fal-ai/leffa/virtual-tryon`,
    `…/fal-ai/leffa/pose-transfer`, and the `…/api` documentation tabs
- Evidence kind: provider documentation (host catalogue metadata, input/output schemas, host pricing)
- Publication date: both endpoints `date` / `publishedAt` 2024-12-17; `updated_at` 2026-04-21 (metadata)
- Capture date: 2026-10-26
- Relevant models: Leffa on fal (`fal-ai/leffa/virtual-tryon`, `fal-ai/leffa/pose-transfer`)

## Endpoints in the catalogue

The keyword query for `leffa` returned two Leffa endpoints and nothing else in the family:

| Endpoint | Title | Category | `date` / `publishedAt` | `status` | `hostingType` | `licenseType` | `machineType` |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `fal-ai/leffa/virtual-tryon` | Leffa Virtual TryOn | image-to-image | 2024-12-17T00:00:00.000Z | public | serverless | commercial | GPU-A100 |
| `fal-ai/leffa/pose-transfer` | Leffa Pose Transfer | image-to-image | 2024-12-17T00:00:00.000Z | public | serverless | commercial | GPU-A100 |

Both carry `kind: "inference"`, `deprecated: false`, `removed: false`, `authSkippable: false`,
`hidePricing: false`, and an empty `githubUrl`. `group.key` is `leffa` with labels "Virtual TryOn" and
"Pose Transfer"; `https://fal.ai/models/fal-ai/leffa` returned HTTP 200 and is the group page the
catalogue points at, while calls go to the two endpoint IDs.

The metadata API adds `"status":"active"` and `"updated_at":"2026-04-21T17:50:46.548Z"` (virtual try-on)
and `"2026-04-21T17:50:45.973Z"` (pose transfer). The `updated_at` is a host-side metadata touch in
2026; the `date` field, which fal uses for the endpoint's publication, is 2024-12-17 for both.

fal's catalogue does not name a model lab, vendor, or upstream repository for either endpoint. The
`licenseType: "commercial"` field and the "Commercial use" badge are fal's statements about use
through fal, not a statement by the model's authors.

## Descriptions (verbatim)

> Leffa Virtual TryOn is a high quality image based Try-On endpoint which can be used for commercial
> try on.

> Leffa Pose Transfer is an endpoint for changing pose of an image with a reference image.

The OpenAPI `x-fal-metadata.about` strings are `Leffa Predict Vt` and `Leffa Predict Pt`. No fal page
cites the paper, the GitHub repo, the checkpoint names, or the training data.

## Pricing (verbatim from the model pages)

Both pages render: "Your request will cost $0.1 per generation." (rendered with a space between the
dollar sign and the number). That is a flat per-call price for either endpoint, with no per-megapixel,
per-step, or input-count component and no `pricingInfoOverride` field in the catalogue JSON for either
entry.

## Virtual try-on schema (`LeffaVirtualTryonInput`)

Required: `human_image_url`, `garment_image_url`, `garment_type`.

| Field | Type | Default / range | Notes (verbatim where quoted) |
| --- | --- | --- | --- |
| `human_image_url` | string | required | "Url for the human image." Example points at `model_tests/leffa/person_image.jpg` |
| `garment_image_url` | string | required | "Url to the garment image." Example points at `model_tests/leffa/tshirt_image.jpg` |
| `garment_type` | enum | required; `upper_body` \| `lower_body` \| `dresses` | "The type of the garment used for virtual try-on." |
| `num_inference_steps` | integer | default 50, 1–50 | "The number of inference steps to perform." |
| `guidance_scale` | number | default 2.5, 0–20 | CFG description |
| `seed` | integer or null | — | "The same seed and the same input given to the same version of the model will output the same image every time." |
| `output_format` | enum | `jpeg` \| `png`, default `png` | |
| `sync_mode` | boolean | default false | data-URI response, excluded from request history |
| `enable_safety_checker` | boolean | default true | "Disabling it requires account authorization; unauthorized requests are always checked, and images flagged as unsafe are returned as black images." |

Output `LeffaVirtualTryonOutput`: `image` (with `width`, `height`, `content_type`, `url`; the schema
example is 768×1024), `seed`, `has_nsfw_concepts`. There is no width, height, aspect-ratio, or
resolution parameter anywhere in the input schema.

## Pose transfer schema (`LeffaPoseTransferInput`)

Required: `pose_image_url`, `person_image_url`. Same `num_inference_steps` (default 50), `guidance_scale`
(default 2.5), `seed`, `output_format`, `sync_mode`, `enable_safety_checker` fields as above.

The two required fields are documented inconsistently on the host:

| Field | Description (verbatim) | Example value (verbatim) |
| --- | --- | --- |
| `pose_image_url` | "Url for the human image." | `…/model_tests/leffa/person_image.jpg` |
| `person_image_url` | "Url to the garment image." | `…/model_tests/leffa/pose_image.jpg` |

The descriptions are copied from the virtual try-on schema (one still says "garment image"), and the
example URLs are crossed: `pose_image_url` is exemplified with `person_image.jpg` and
`person_image_url` with `pose_image.jpg`. Which field supplies the pose and which supplies the person
therefore cannot be settled from fal's documentation alone. The first-party semantics (see the GitHub
record) are that the source image supplies the pose — via DensePose extracted from it — and the
reference image supplies appearance; so by the upstream naming, `pose_image_url` should be the source
and `person_image_url` the appearance reference, which is the opposite of what the example URLs imply.

Output `LeffaPoseTransferOutput`: `image`, `seed`, `has_nsfw_concepts`; the schema example is 1024×768.

## Gaps

- No statement of which upstream checkpoint (VITON-HD `virtual_tryon.pth`, DressCode
  `virtual_tryon_dc.pth`, or DeepFashion `pose_transfer.pth`) either endpoint runs, or whether fal
  re-hosted, converted, or fine-tuned the weights.
- No resolution, aspect-ratio, or crop control in either schema; output size is fixed by the
  implementation and is only visible in the schema's example output.
- No documented latency, cold-start, or queue behaviour; `machineType: GPU-A100` is the only hardware
  statement.
- No page-level changelog for the `updated_at` 2026-04-21 change, so whether anything behavioural
  changed on that date is unknown.
- The pose-transfer field descriptions and examples contradict each other (above); no erratum was
  found on the page.

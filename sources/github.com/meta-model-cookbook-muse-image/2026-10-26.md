## Recipe 01 — captured content (verbatim)

Header table: Section "Muse Image"; Model **`muse-image-1.0`**; Prerequisites "Python 3.10+, the
`openai` package, and a `MODEL_API_KEY`".

> Muse Image is a reasoning model that generates and edits images from a text prompt. It plans a
> request before it renders, so multi-part prompts hold together. You drive it through the
> conversational Responses API: point your client at `https://api.meta.ai/v1`, set your key, and
> call `client.responses.create(...)`. Each call is a turn in a conversation. The first turn
> generates an image, and later turns refine it. The server keeps the conversation state, so a
> follow-up turn sends only the new instruction and the image carries forward on its own.

> Muse Image is a separate model family from Muse Spark: it **outputs images** rather than text.

> **Later turns** pass `previous_response_id` set to the prior response's `id`. […] **Reference
> images** ride along as `input_image` content parts inside a `{"role": "user", "content": [...]}`
> message. The model draws on them to guide the render (style, subject, pose, layout) without
> necessarily copying them into the output. Pass several to compose them into one scene or to
> combine their influences. Attach only images the server does not already have.

Output shape, verbatim example:

```json
{
  "id": "resp_...",
  "status": "completed",
  "output": [
    { "type": "reasoning", "id": "rs_..." },
    { "type": "message", "id": "msg_...", "content": [ ... ] },
    { "type": "image_generation_call", "id": "ig_...", "status": "completed", "result": "UklGR..." }
  ],
  "usage": { "input_tokens": 9996, "output_tokens": 908, "total_tokens": 10904 }
}
```

Token usage recorded in the recipe (illustrative, not a benchmark):

| Turn | input_tokens | cached_tokens | output_tokens | reasoning_tokens | total |
| --- | --- | --- | --- | --- | --- |
| generate (fox) | 9,996 | 7,936 | 908 | 161 | 10,904 |
| refine (add hat) | 13,710 | 10,560 | 572 | 57 | 14,282 |
| compose (3 references) | 16,458 | 11,072 | 1,070 | 282 | 17,528 |

Constraint on reference images:

> The content parts must be wrapped in a `{"role": "user", "content": [...]}` message. A bare list
> of content parts is rejected with an HTTP 400.

Stateless mode:

> A `store` parameter controls this and defaults to `true`, so the server stores each turn and the
> next one can chain from it. If you would rather not keep state on the server, set `store=False`.
> You then carry the conversation yourself: to continue from a prior render, replay its
> `image_generation_call` item as an input on the next turn instead of passing
> `previous_response_id`.

## Summary

The cookbook confirms the model ID `muse-image-1.0` and the API base URL, documents the
conversational chaining model (`previous_response_id`, server-held state, `store=False` fallback),
and shows that reference images are `input_image` parts that guide style/subject/pose/layout
"without necessarily copying them into the output". It also documents the 400 on bare content-part
lists. Its token counts show that image responses are metered in tokens for reporting even though
the price is per image.

## Gaps

- **No capability limits** — no maximum number of reference images, no input image size ceiling, no
  prompt length limit.
- **No quality or latency numbers**; the recipe says results are non-deterministic and "your results
  will differ".

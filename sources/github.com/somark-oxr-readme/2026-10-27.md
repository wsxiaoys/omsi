## Code layout, from the file tree

- `oxr/pipeline/` — the parsing pipeline: `layout.py`, `recognition.py`, `reading_order.py`,
  `assembler.py`, `orchestrator.py`, `concurrency.py`, plus a `postprocess/` package with separate
  handlers for tables, formulas, code, chemical structures, pictures, layout, JSON and several
  de-duplication passes.
- `oxr/pipeline/_vendor/xycut_plus_plus.py` and `oxr/pipeline/xycut_order.py` — a vendored
  XY-cut reading-order implementation, i.e. reading order is not purely model-predicted.
- `oxr/model/client.py`, `oxr/model/layout_client.py`, `oxr/model/prompts.py` — clients for the two
  model services and the task prompts.
- `oxr/server/` — FastAPI application plus a bundled demo UI, which vendors KaTeX and
  highlight.js and carries a `LICENSE-SoMarkDownViewer` file.
- `services/` — the OXR model service and the layout-analysis service, each with its own
  environment; `docker/Dockerfile.allinone` builds the combined image.
- `docs/benchmark.md` plus `docs/frozen-100-pages.json` (the frozen speed workload).

## README, verbatim highlights

> OXR (Optical Everything Recognition) is an open-source model from the SoMark team. It turns PDFs
> and document images into Agent-Friendly data in Markdown or JSON, with layout coordinates
> included.

> With just 1.3B parameters, OXR ranks #1 on olmOCR-Bench, OmniDocBench, and DocParsingBench while
> delivering industry-leading parsing speed.

> OXR is the first to make its layout analysis module independent and pluggable. This design
> accelerates parsing and supports replacing the built-in layout model with a custom one.

> With only 1.3B parameters, OXR ranks 🏆#1 among open-source document parsing models in speed tests
> on the RTX PRO 6000.

> OXR supports vLLM, but the official vLLM release does not yet support OXR inference. We provide
> an out-of-tree plugin and a loading script in the model weights folder on Hugging Face. No
> recompilation is needed.

## Summary

First-party confirmation that the release is **code plus weights plus a deployment recipe**, not an
API-only launch: a Docker all-in-one image, a three-service from-source path, an out-of-tree vLLM
plugin, and a bundled demo. It also shows the pipeline is more than the model — XY-cut reading
order, per-element post-processing, de-duplication and assembly are all in the repository, so
"model" benchmarks and "pipeline" behaviour are not the same object.

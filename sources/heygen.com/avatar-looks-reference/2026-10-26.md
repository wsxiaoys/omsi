# HeyGen: Avatar Looks reference (`supported_api_engines`)

- Origin: HeyGen developer documentation, "Avatar Looks",
  <https://developers.heygen.com/docs/avatar-looks> (Markdown at `/docs/avatar-looks.md`)
- Evidence kind: official API documentation (first-party)
- Publication date: none stated. The changelog records "Avatar Engine Metadata Updates" for
  `supported_api_engines` as "Changed - May 2026".
- Capture date: 2026-10-26
- Relevant models: HeyGen Avatar V eligibility gate

## Captured content (verbatim)

Look object example:

```json
{
  "id": "lk_abc123",
  "name": "My Digital Twin",
  "avatar_type": "digital_twin",
  "supported_api_engines": ["avatar_iv", "avatar_v"]
}
```

> `supported_api_engines` | array | Engine values this look accepts for `POST /v3/videos`: `"avatar_iii"`,
> `"avatar_iv"`, and/or `"avatar_v"`. Check this array before requesting a specific `engine` — requesting
> an engine that isn't listed returns `invalid_parameter`.

> Once you have a look `id`, pass it as `avatar_id`. When you request a specific rendering engine, pick
> one from the look's `supported_api_engines` array — for example, pass `"engine": {"type": "avatar_v"}`
> when the array includes `"avatar_v"`. Omitting `engine` uses Avatar IV.

The endpoint is `GET /v3/avatars/looks` (cursor-paginated, default 20 / max 50 per page, per the usage
limits record) with filters including `avatar_type` and `ownership`.

## Summary

This is the mechanical form of Avatar V's per-look gate: an array on the look, readable before a render
is requested, whose absence of `"avatar_v"` produces `invalid_parameter`. The example shows a digital
twin advertising both `avatar_iv` and `avatar_v`, consistent with the engine comparison table.

Note the error code differs between first-party documents: `invalid_parameter` here, versus "HeyGen
returns 400 otherwise" in fal's schema description. The two are consistent (400 with an
`invalid_parameter` code) but neither page spells out the full error body.

## Gaps

- No description of how a look acquires `avatar_v` — nothing about training inputs, creation date, or
  plan influencing the array.
- No way to request eligibility, and no documented backfill/upgrade process for older avatars.
- The array is per look, not per avatar group, but the docs do not say whether looks in one group can
  disagree.

## Self-description, verbatim

> MLX conversion of SoMarkAI/OXR-1.0, the document-parsing model from the SoMark team (#1 on
> olmOCR-Bench, OmniDocBench and DocParsingBench), for Apple Silicon via mlx-vlm.

> **This is an unofficial community conversion.** All credit for the model goes to SoMark; see the
> official repository.

## Conversion details, verbatim

| | |
| --- | --- |
| Base model | SoMarkAI/OXR-1.0 (1.3B, BF16) |
| Precision | 8-bit affine (group size 64) for the Qwen3 decoder; the visual tokenizer (ViT, visual head, visual embedding table) stays in bfloat16 |
| Size | 2.1 GB |
| Converted with | `mlx_vlm.convert` (`-q --q-bits 8 --q-group-size 64`) |

Note the card's own decomposition: a **Qwen3 decoder** plus a visual tokenizer made of ViT, visual
head and visual embedding table — the same split the vendor describes, and further evidence that the
language backbone is Qwen3-derived
([launch post](../../somark.ai/oxr-launch-post/2026-10-27.md)).

## Validation, verbatim

> Greedy outputs compared with the reference PyTorch implementation (fp32, CPU) on text, LaTeX
> formula, code, handwriting, a whole page (1,859 tokens) and a complex HTML table (3,603 tokens):
> identical to the bf16 conversion on 5 of 6 samples (incl. the 1,859- and 3,603-token outputs); one
> handwriting sample differs by one word.

> Full OXR pipeline with an MLX backend on olmOCR-Bench (official `olmocr==0.4.27` evaluator,
> 596 pages / 3,849 tests, bf16): **87.6 ± 1.0** overall vs **87.84** reported for OXR-1.0 — ArXiv
> 91.2 (92.76), Headers/Footers 95.8 (94.34), Long Tiny Text 91.0 (90.95), Multi Column 84.1
> (85.18), Old Scans 58.9 (59.32), Old Scans Math 89.3 (89.74), Tables 93.3 (93.05), Baseline 97.1
> (97.35).

> The olmOCR-Bench numbers above were measured with bf16 weights. The 8-bit decoder is ~35% faster on
> long outputs; no full benchmark run was done for it yet — prefer the bf16 repo when exactness
> matters.

## What this establishes

- **The weights load and run outside the vendor's stack.** This is the only third-party artefact
  found that both converts and executes the model, and it reproduces the vendor's headline
  olmOCR-bench level within its own error bar: 87.6 ± 1.0 against 87.84.
- **The reproduction is partial.** It covers 596 pages and 3,849 tests, against the vendor's 1,403
  pages and 8,413 rules. It therefore supports the **level**, not the **rank**: no peer model was
  re-run, so the 0.24-point lead over Infinity-Parser2-Pro is untouched by this evidence.
- **The component scores drift in both directions** (Headers/Footers +1.5, Multi Column −1.1,
  ArXiv −1.6), consistent with a subset run rather than a systematic bias.
- **The architecture claim is independently corroborated**: a Qwen3 decoder plus a bf16 visual
  stack is what a third party actually had to convert.

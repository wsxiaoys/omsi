## Positioning, verbatim

> An open-source document parsing model with SOTA accuracy and speed, using an RSI loop during
> post-training.

> OXR (Optical Everything Recognition) is an open-source model from the SoMark team. It turns PDFs
> and document images into Agent-Friendly data in Markdown or JSON, with layout coordinates
> included.

> Pretrained from scratch, OXR uses a recursive self-improvement (RSI) loop during post-training—a
> first in document parsing. With just 1.3B parameters, OXR ranks #1 on olmOCR-Bench,
> OmniDocBench, and DocParsingBench while delivering industry-leading parsing speed.

> OXR is the first to make its layout analysis module independent and pluggable.

## Element types, verbatim

Thirteen types, with the JSON `type` value and output format for each: Caption (plain text),
Footnote (plain text), Formula (LaTeX), Text (plain text), Page-footer (plain text, filtered out by
default), Page-header (plain text, filtered out by default), Picture (image), Title (plain text),
Table (HTML / Markdown), Stamp (plain text / image), Chemical Equation (LaTeX starting with `\ce`,
mhchem syntax), Code Block (Markdown code block), Chemical Structure (SMILES / image).

## Architecture, verbatim

> The system consists of two models: a Layout Analysis model and OXR. We integrate Reading Order
> into the Recognition stage, with both tasks handled by the same model.

> Existing document parsing tools either assign it to the Recognition model or use a dedicated
> model that also handles Reading Order. OXR's design achieves the simplest access method for
> Layout Analysis, and any Layout Analysis model can work well with the OXR model.

The card does not state the parameter count of the layout model, the vision encoder, or the
language backbone.

## Running it, verbatim

- "Operating system: Linux"; "GPU: NVIDIA (with BF16 support)"; "Driver: NVIDIA driver
  (compatible with CUDA 13.0)"; "Python: 3.12"; "GPU memory to get started: 24GB on a single GPU
  (for low-concurrency testing)"; "Recommended GPU memory: ≥48GB on a single GPU (for long
  documents / higher concurrency)".
- Weights: BF16, "Includes a lightweight layout analysis model? Yes, in the layout_analysis
  folder". Download via `hf download SoMarkAI/OXR-1.0` or ModelScope `SoMark/OXR-1.0`.
- Docker path: `docker build -f docker/Dockerfile.allinone -t oxr-1.0 .`, run with
  `--gpus all --ipc=host -p 127.0.0.1:8000:8000`; demo at `:8000/demo`, OpenAPI at `:8000/docs`;
  "The default startup timeout is 900 seconds."
- From source: three services — OXR model service on 8080, layout analysis on 8081, document
  parsing API on 8000. `pip install vllm==0.25.1 transformers==5.13.1`; "OXR supports vLLM, but the
  official vLLM release does not yet support OXR inference. We provide an out-of-tree plugin and a
  loading script in the model weights folder".
- Layout runtime: `torch==2.11.0 torchvision==0.26.0` from the cu130 index.
- API: `POST /v1/parse/sync` with `file`, `api_key`, `output_formats` (markdown, json); compatible
  with the SoMark API, CLI and SDK by changing the base URL.

## Summary

First-party confirmation of: a single BF16 checkpoint with a bundled layout model, 13 element
types, a two-stage layout-then-recognise pipeline with reading order folded into recognition, a
pluggable layout stage, a free keyless API with 10 MB / 20-page limits, and a custom licence. The
card asserts "#1 on olmOCR-Bench, OmniDocBench, and DocParsingBench" but prints **no scores**; the
numbers live in the repository's `docs/benchmark.md`
([benchmark](../../github.com/somark-oxr-benchmark/2026-10-27.md)).

## Gaps and internal tensions

- **"1.3B parameters" against 1,534,378,216 BF16 parameters in the weights file.** The card gives
  no breakdown, so it is unclear whether the 1.3B figure excludes the layout model, the vision
  encoder, or is rounded down from 1.53B. Independent reporting noticed the same gap
  ([Webdiga](../../webdiga.com/oxr-document-parsing/2026-10-27.md)).
- **"Pretrained from scratch" is stated without qualification, but the card's own architecture
  description elsewhere names `Qwen3-0.6B-Base` as the language model.** The launch post says the
  visual embeddings are concatenated "into a sequence for Qwen3-0.6B-Base", and `config.json`
  carries `llm_config._name_or_path: "Qwen/Qwen3-0.6B-Base"`
  ([weights metadata](../../huggingface.co/somark-oxr-1-0-weights-metadata/2026-10-27.md)). The
  claim is therefore about the parsing model as a whole, not about every component being trained
  from random initialisation; the card does not say which reading it intends.
- No training-data description, no data cutoff, no language coverage statement, and no statement
  of what the RSI loop's "general VLM" judge was.
- No latency, throughput or cost figures on the card; speed claims also live in `benchmark.md`.
- No statement about non-Latin scripts beyond the example images (Chinese handwriting, vertical
  text).

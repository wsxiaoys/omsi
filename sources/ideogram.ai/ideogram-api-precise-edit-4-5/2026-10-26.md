- Relevant models: Ideogram 4.5 (endpoint `POST https://api.ideogram.ai/v2/image/precise-edit/ideogram-4-5`,

## Captured content

### Summary and the resolution cap (verbatim)

> Edit an image with Ideogram 4.5 and get the result back at that image's exact width and height.
> Upload the image as `image` using `multipart/form-data`, with optional `reference_images` and a
> `mask`.

> Editing the whole image is bounded by 4194304 pixels (the area of a 2048x2048 square), so a
> larger image comes back scaled down to fit: an 8192x8192 image returns as 2048x2048.
>
> To edit a 4K or 8K image at its full resolution, set `context_window` to confine the edit to one
> region, either `auto` together with a `mask`, or `y_min,x_min,y_max,x_max` to name the region
> yourself. Only that region changes, the rest of the image comes back unchanged, and the result
> keeps the image's own width and height at any input size.

### Parameters that constrain behavior (verbatim)

- `image`: "the image to edit, as raw bytes (max 50MB and 67108864 pixels, which 8192x8192 meets
  exactly; JPEG, PNG, or WEBP). […] The output always matches this image's width and height, and
  pixels the edit did not meaningfully change are copied exactly from it."
- `reference_images`: "Optional images to guide the edit (max 4, max 50MB each […]). They are
  never edited themselves; only `image` is. […] A request with a `mask` can include at most three,
  because the mask takes up one reference slot."
- `mask`: "Black marks the area to edit and white the area to keep; values in between are rounded
  to the nearer of the two. The mask must have the same width and height as the image being edited
  and contain both black and white areas."
- `context_window`: "`none`, the default, edits the whole image, which is bounded by 4194304
  pixels […] `auto` requires a `mask` and fits a region around the masked area. […] It must lie
  inside the image, measure at least 256px on each side, have an aspect ratio between 1:6 and 6:1,
  and cover no more than 4194304 pixels."
- `quality`: "`very_low` is the fastest and cheapest, and `high` takes longer and is priced higher.
  This is the only field that affects the price: the size of the image you send does not change
  it, and neither does `context_window`."
- Same `enable_copyright_detection`, `seed`, `num_images`, `async`, `webhook_url`, and `dry_run`
  semantics as the Generate endpoint.

### Pricing basis (verbatim)

> This is the only field that affects the price: the size of the image you send does not change
> it, and neither does `context_window`.

For Precise Edit, price depends on quality only — not on resolution, input size, or reference
count. That matches the product page's "Each image has a fixed price"
([model page](../ideogram-4-5-model-page/2026-10-26.md)) and contradicts the Generate
reference's pixel-tier statement for the Generate endpoint
([Generate reference](../ideogram-api-generate-4-5/2026-10-26.md)).

## Known gaps

- The reference does not state a price per quality tier; only that quality is the sole price
  variable.
- No published latency figures or failure-rate data for large `context_window` edits.

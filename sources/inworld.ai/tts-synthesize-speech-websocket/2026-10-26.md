## Transport and latency framing

> Open a persistent WebSocket connection and send text messages. The server streams audio chunks over
> the same connection, avoiding per-request overhead and repeated handshakes for the lowest possible
> latency.

> Messages on a connection are processed in order, so you don't need to wait for the `contextCreated`
> acknowledgment before sending text. For the lowest latency, send each message as soon as it is
> ready — waiting for the acknowledgment adds a full network round trip before the first audio chunk
> arrives.

The page publishes **no latency number of its own** — no ms figure for TTFB, per-message processing,
or round trip. Latency numbers for the models live on the models page (100 ms / 20 ms P90,
server-side) and in the launch copy ("sub-200ms"); this page establishes only the ordering argument
(pipelining avoids one network round trip).

## Three text-buffering modes

| Input shape | Mode | Who triggers synthesis |
| --- | --- | --- |
| Full text, app controls batching | manual — `autoMode: false` (default) | app calls `flushContext` / `closeContext` |
| App already splits into sentences | `autoMode: true`, `CLIENT_SEGMENTED` | server schedules the segments sent |
| Partial text / LLM tokens | `autoMode: true`, `SENTENCE_BOUNDARY` | server detects sentence boundaries in the incoming stream |

> `SENTENCE_BOUNDARY` supports `inworld-tts-2` and `inworld-tts-2-flash` where those models are
> available. Selecting it with auto mode enabled on an unsupported model returns `INVALID_ARGUMENT`.

`autoMode: true` alone selects `CLIENT_SEGMENTED`. A tag may span messages (`"[whis"` then
`"per] Hello."`) and incomplete markup at flush/close returns `INVALID_ARGUMENT`.

## Limits and metering

| Limit | Detail |
| --- | --- |
| 2,000 characters per `sendText` message | "Split longer input across multiple messages" |
| UTF-16 code units | both the limit and billed usage count UTF-16 units; "many emoji count as two" |
| Context text not billed | only `sendText` text counts toward character usage |
| `synthesisContext` | up to 5 earlier texts, 2,000 characters combined; more returns `INVALID_ARGUMENT` |
| Buffering safeguards | server "can flush accumulated text before your app requests it" |

Timestamps can be delivered `SYNC` (default, audio + timestamps per chunk) or `ASYNC` (audio first,
timestamps trailing) — the latter is documented as reducing time-to-first-audio.

## Summary

The WebSocket route is the vendor's lowest-latency transport and the only one that accepts
LLM-token streaming directly, but it is also the route with the smallest published limit (2,000
characters per message, UTF-16 counted) and no published latency figure. Both independent hosts in
this corpus expose the 2,000-character non-streaming call only, so nothing in the corpus measures the
WebSocket path.

## Gaps

- No ms-level latency for the WebSocket transport, with or without pipelining, so the "lowest
  possible latency" claim cannot be checked against the REST numbers.
- Connection and concurrency limits are delegated to a separate rate-limits page not captured here.
- No statement of whether `SENTENCE_BOUNDARY` is unavailable on TTS-1.5 for quality or for
  implementation reasons.

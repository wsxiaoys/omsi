# Meshy: Rate limits (by plan)

- Origin: Meshy Docs, "Rate limits", https://docs.meshy.ai/en/api/rate-limits
- Evidence kind: official documentation (vendor policy)
- Publication date: none stated; live policy as of capture.
- Capture date: 2026-10-26
- Relevant models: every Meshy API generation, including Meshy 7.1

## Captured content (verbatim table)

"Meshy limits each account in two ways: Requests per second ... Concurrent tasks: how many of your
tasks can be PENDING or IN_PROGRESS at the same time."

| Plan | Requests per second | Concurrent tasks | Priority |
| --- | --- | --- | --- |
| Pro | 20 | 10 | Default |
| Premium | 20 | 30 | Higher than Pro |
| Ultra | 20 | 100 | Highest |
| Studio | 20 | 60, or 20 on some earlier Studio plans | Higher than Pro |
| Enterprise | 100 | 100 by default, or a custom limit | Highest |

"Every API request counts toward requests per second, including requests that get, list, or stream
tasks. Requests from the Meshy web app don't count." The concurrent-task limit "counts tasks, not
requests."

Over-limit behaviour: 429. "Too many requests per second: the message is `Rate limit exceeded`. Wait
the number of seconds in the `Retry-After` header"; too many concurrent tasks: "the message starts with
`NoMorePendingTasks` ... This 429 has no `Retry-After` header."

Headers: `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`, `Retry-After`.

## Summary

Throughput on Meshy 7.1 is plan-gated at 20 requests/second for every non-Enterprise plan, with the
concurrent-task ceiling ranging from 10 (Pro) to 100 (Ultra). Because a 7.1 text-to-3D run is two
requests (preview, then refine), the effective pipeline rate is half the request budget.

## Gaps

- No per-endpoint latency figures, so concurrency cannot be converted to throughput from this page.
- No statement of whether Ultra 4K tasks are queued differently from Standard ones.

## Captured content (verbatim)

Structure:

> Send a conversation as a list of messages with the roles `system`, `user`, `assistant`, and
> `tool`. The first message can be a `system` (or `developer`) message with your system prompt.

> The rendered system message contains, in this order:
>
> 1. The default lines: `You are a helpful AI assistant.`, the knowledge cutoff (2026-01-04), and
>    the current date
> 2. Your system prompt, if you send one
> 3. The tool definitions, if you pass `tools`
> 4. The reasoning strength, unless your system prompt sets one
> 5. The list of recipients the model can address its messages to

Rendered prompt example:

> `<|begin_of_text|><|start|>system<|message|>You are a helpful AI assistant.`
>
> `Knowledge cutoff: 2026-01-04.`
>
> `Current date: 2026-10-15.`

Recipients:

> The model addresses each of its own messages to a recipient: `self` for reasoning, `commentary`
> for updates shown while it keeps working, a tool name for a tool call, and `user` for the final
> answer.

Reasoning control:

> Muse Spark Open always reasons before it answers. Set how much with `reasoning_effort` on the
> request.

| `reasoning_effort` | Reasoning strength |
| --- | --- |
| `low` | 8 |
| `medium` | 32 |
| `high` | 256 |
| `xhigh` (default) | 512 |

> Reasoning can't be turned off. Any value other than these four, such as `none` or `max`, is
> rejected.

> A server started with the `muse` reasoning parser returns the reasoning in its own field, separate
> from the answer in `content`. Higher strengths produce long reasoning, so request streaming
> (`stream: true`) to avoid timeouts.

Tool calling:

> Pass your tools in `tools`, in the OpenAI function-calling format. When the model wants a tool, the
> response has `tool_calls` instead of an answer. […] Repeat until the response has no `tool_calls`;
> its `content` is the answer.

> The model can ask for several tools in one response […] Answer every call with its own `tool`
> message before you send the next request.

> The template lists your `tools` in the system message. When the model calls a tool, it writes the
> call in ATEM format, and the template wraps each result in `<tool_output>`.

Media input:

> Pass media as typed content parts in a `user` message, alongside text:
>
> ```json
> {"role": "user", "content": [
>   {"type": "image_url", "image_url": {"url": "https://example.com/chart.png"}},
>   {"type": "video_url", "video_url": {"url": "https://example.com/demo.mp4"}},
>   {"type": "audio_url", "audio_url": {"url": "https://example.com/question.wav"}},
>   {"type": "text", "text": "Answer the question in the recording."}]}
> ```

> For video, use clips longer than a few seconds at 448 px or more on the short side. On very short
> or low-resolution clips, such as a few seconds at around 100 px, the model can reply that it can't
> view the video.

> The template writes a placeholder for each media part, `<|patch|>` for an image, `<|video|>` for a
> video, and `<|audio|>` for audio, and the multimodal processor replaces each one with that media's
> tokens.

## Summary

The guide documents a mandatory-reasoning model with four numeric reasoning strengths (`low` 8 to
`xhigh` 512, default `xhigh`), an OpenAI-style `tools` loop with parallel calls rendered in ATEM
format, and three media content-part types (`image_url`, `video_url`, `audio_url`). The knowledge
cutoff baked into the chat template is **2026-01-04**. Video quality has a documented floor: clips
longer than a few seconds at ≥448 px on the short side, or the model may refuse to view them.

## Gaps

- No token cost or context accounting for media: no per-image, per-video-second, or per-audio-minute
  token formula.
- No limits on the number of media parts, image resolution ceilings, video duration ceilings, or
  audio sample-rate requirements.
- No statement of which languages the model is prompted in, despite the overview's "more than 100
  languages" claim.

# xAI API reference: image generation and editing endpoints

- Origin: xAI developer documentation
  - "Inference API — Images", <https://docs.x.ai/developers/rest-api-reference/inference/images>
  - OpenAPI specification, <https://docs.x.ai/openapi.json>
- Evidence kind: official documentation (machine-readable API contract)
- Publication date: none stated; live document
- Capture date: 2026-10-26
- Relevant models: `grok-imagine-image`, `grok-imagine-image-2.0` (the `model` example in the
  OpenAPI request schemas is `grok-imagine-image`)

## Endpoints

`POST /v1/images/generations` and `POST /v1/images/edits`, both `application/json`.

## Request fields (verbatim, abridged to the fields that constrain capability)

> * `aspect_ratio` ("1:1" | "3:4" | "4:3" | "9:16" | "16:9" | "2:3" | "3:2" | "9:19.5" | "19.5:9" |
>   "9:20" | "20:9" | "1:2" | "2:1" | "21:9" | "5:2" | "auto")
> * `deferred` (boolean | null) — If set, the request returns immediately with a `request_id` and
>   the image is generated in the background. […] Only `response_format: "url"` is supported in
>   this mode.
> * `model` (string | null) — Model to be used.
> * `n` (integer | null) — Number of images to be generated
> * `prompt` (string) — Prompt for image generation.
> * `resolution` ("1k" | "2k" | "1.5k")
> * `response_format` (string | null) — Response format to return the image in. Can be url or
>   b64_json.
> * `user` (string | null) — A unique identifier representing your end-user, which can help xAI to
>   monitor and detect abuse.

## OpenAPI schema details (verbatim from `openapi.json`)

`components.schemas.ImageResolution`:

> "description": "Resolution for image generation.\nOnly supported by grok-imagine models."
> "enum": ["1k", "2k", "1.5k"]

`components.schemas.GenerateImageRequest.properties.model`:

> "description": "Model to be used.",
> "example": "grok-imagine-image"

`components.schemas.GenerateImageRequest.properties.n`:

> "description": "Number of images to be generated",
> "default": 1, "maximum": 10, "minimum": 1

`components.schemas.GenerateImageRequest.properties.resolution`:

> "description": "Resolution of the generated image. Defaults to `1k`.\nOnly supported by
> grok-imagine models."

`components.schemas.EditImageRequest.properties.images`:

> "description": "List of input images for multi-reference editing.\nMutually exclusive with
> `image`. When multiple images are provided, refer to them as \<IMAGE_0\>, \<IMAGE_1\>, etc. in the
> prompt."

`components.schemas.EditImageRequest.properties.aspect_ratio`:

> "description": "Aspect ratio of the output image for image editing with multiple images.\nFor
> single image editing, do not set this. It will always auto-detect from the input image."

## Two contradictions inside the first-party contract

1. **Resolution enum.** The REST reference and the OpenAPI schema both enumerate `1k`, `2k`, and
   **`1.5k`**, while the generation guide says "Currently supported image resolutions are: `1k`
   (default when omitted), `2k`". No documentation page explains what `1.5k` is or which models
   accept it. fal exposes only `1k` and `2k`.
2. **`quality` is undocumented in the contract.** The generation guide documents a `quality`
   parameter (`low` / `medium` / `auto`) for `grok-imagine-image-2.0`, and the August 2026 release
   note and the November 2 migration guide both depend on it. Neither the REST reference's request
   field list nor `GenerateImageRequest` / `EditImageRequest` in `openapi.json` contains a `quality`
   property. A client generated from the OpenAPI spec cannot send it.

## What this establishes

- `grok-imagine-image` is the **schema example model**, i.e. the default illustrative model ID in
  xAI's own API contract, even though every guide example uses 2.0.
- Up to **10** images per request; `n` is bounded at the schema level.
- Multi-image editing uses `<IMAGE_0>`, `<IMAGE_1>` positional references in the prompt, and the
  single-image edit path deliberately ignores `aspect_ratio`.
- `deferred` requires URL output; base64 and deferred are mutually exclusive.
- `user` exists as an abuse-monitoring identifier on the image endpoints (the newer
  `safety_identifier` field is documented for text endpoints only).

## Gaps

- No per-model capability matrix, so the schema cannot tell a client which of the three image tiers
  supports `1.5k`, five references, or `quality`.
- No documented error codes for policy refusals on these endpoints.

# MiMo API multimodal input limits — image, video, audio

- **Origin:** three sibling docs on the Xiaomi MiMo API Open Platform:
  1. "Image Understanding", <https://mimo.mi.com/static/docs/quick-start/usage-guide/multimodal-understanding/image-understanding.md>
  2. "Video Understanding", <https://mimo.mi.com/static/docs/quick-start/usage-guide/multimodal-understanding/video-understanding.md>
  3. "Audio Understanding", <https://mimo.mi.com/static/docs/quick-start/usage-guide/multimodal-understanding/audio-understanding.md>
  All retrieved 2026-10-26.
- **Evidence kind:** official documentation (first-party API usage guides).
- **Publication date:** none stated. The worked examples' system prompt says "Today is date:
  Tuesday, December 16, 2025" — a leftover from the MiMo-V2-Flash launch — so the *examples* are
  older than the model support statements; the support statements name V2.6 explicitly.
- **Capture date:** 2026-10-26
- **Relevant models:** `mimo-v2.6-flash`, `mimo-v2.6-pro`, `mimo-v2.6-pro-ultraspeed` ("Currently,
  the … models are supported" on all three pages).
- **Capture type:** full raw Markdown; the token-estimation code blocks are quoted, not executed.

## Inputs and hard limits, verbatim

**Image** — "Image Formats: JPEG, PNG, GIF, WebP, BMP"; URL or Base64; "single image file size
does not exceed 50 MB" (50 MB also for the Base64 string); count "limited by the model's context
length". Scaling constants in the token calculator: `PATCH_SIZE = 16`, `SPATIAL_MERGE_SIZE = 2`,
`TEMPORAL_PATCH_SIZE = 2`, `IMAGE_MIN_PIXELS = 8192`, `IMAGE_MAX_PIXELS = 8388608`.

**Video** — "Video Formats: MP4, MOV, AVI, WMV"; "single video file size does not exceed 300 MB"
by URL, "50 MB" as a Base64 string; count "limited by the model's context length".

> "`fps` is the frame number of images extracted from the video per second … The default value is
> 2, with a range of `[0.1, 10]`."

> "`media_resolution` … `default`: The default level, balancing recognition effectiveness and
> processing efficiency; `max`: The highest resolution level, which enhances the recognition
> ability for small objects and detailed textures."

**Audio** — "single audio file size cannot exceed 100 MB" by URL, 50 MB as Base64; count limited
by context length.

> "Total tokens ≈ Audio duration (in seconds, e.g., 10.6 seconds) * 6.25"

## Billing basis, verbatim (all three pages)

> "Billing: The total cost is calculated based on the number of input, input (cache hits), and
> output tokens."

`usage.prompt_tokens_details` reports `image_tokens`, `video_tokens` and `audio_tokens`
separately; the video example also bills `audio_tokens` for the video's audio track.

## What this establishes

- All three modalities are **input-only**; nothing on any captured page describes image, audio or
  video *output* from V2.6. Output is text everywhere.
- Media is metered as input tokens with published conversion rules, so a video's cost is a
  function of duration, `fps` and `media_resolution` — the two knobs the docs expose.
- There is no per-file duration cap for audio or video; the binding constraint is the 1M-token
  context, which for audio at 6.25 tokens/second is ~44 hours of audio in a single request before
  any text is counted.

## Gaps

- No stated minimum or maximum video duration, no frame-resolution table, no per-request media
  count limit.
- No refusal or safety policy for media (e.g. faces, violence) on any of the three pages.
- The docs do not say whether `media_resolution: max` changes the token rate beyond the scaling
  constants in the image calculator.
